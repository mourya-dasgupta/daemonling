# Decision Log

Every non-obvious product or engineering call made while building the MVP. Format: decision,
alternatives considered, why. Newest decisions are appended at the bottom of each milestone.

## M0 — Foundations

### D-001 Branch name

- **Decision:** Work on `feat/daemonling-mvp` as the founder asked. The cloud session was created
  with a different default branch (`claude/busy-goldberg-m8aoai`); we push the same commits there too
  only if pushing to `feat/daemonling-mvp` is refused.
- **Alternatives:** Use only the session branch.
- **Why:** The founder's brief names the branch explicitly and the PR body refers to it.

### D-002 Workspace packages resolve to TypeScript sources in dev, `dist` in production

- **Decision:** Each workspace package's `exports` has a custom `daemonling-source` condition pointing
  at `src/index.ts`. TypeScript (`customConditions`), Vitest/Vite (`resolve.conditions`) and esbuild
  (`conditions`) use it; `tsc` builds and plain Node fall back to `dist`.
- **Alternatives:** TS project references (`tsc -b`); path aliases; always building before testing.
- **Why:** Tests and typechecks need no prior build step, bundles never go stale, and published
  packages still work as normal compiled ESM.

### D-003 Library modules use NodeNext + explicit `.js` import extensions

- **Decision:** `packages/*` and `apps/cli` compile with `module: NodeNext`; the web app uses
  `moduleResolution: Bundler`.
- **Alternatives:** Bundler resolution everywhere.
- **Why:** The compiled libraries are valid Node ESM without a bundler, which keeps the npm story
  simple.

### D-004 Bundle the CLI and the VS Code extension with esbuild

- **Decision:** `apps/cli` → single `dist/dmn.js` (ESM, shebang); `apps/vscode` →
  `dist/extension.cjs` (CommonJS, `vscode` external).
- **Alternatives:** Ship `tsc` output with `node_modules`.
- **Why:** One file loads fast (important for `dmn prompt` < 50 ms) and the `.vsix` needs no
  dependencies (`vsce package --no-dependencies`).

### D-005 Tool versions

- **Decision:** TypeScript 5.9, Vitest 3.2, ESLint 9, Vite 7, React 19, esbuild 0.25.
- **Alternatives:** The newest majors (TypeScript 7, Vitest 5, ESLint 10).
- **Why:** The brief fixes TypeScript 5; the other picks are the newest lines with long, stable
  track records together.

### D-006 Coverage gate scope

- **Decision:** CI enforces ≥ 90% lines/branches/functions/statements for `packages/core/src/**`
  only; other packages are reported but not gated.
- **Alternatives:** One global threshold.
- **Why:** The brief gates the engine. UI glue code (VS Code activation, React entry) is better
  covered by pure-function tests than by chasing a global number.

## M1 — Core engine

### D-007 `PET_CREATED` carries `id` and optional `settings`

- **Decision:** `PET_CREATED{ id, name, settings? }`. The id is generated by the caller (CLI/web use
  `crypto.randomUUID()`), never by the engine.
- **Alternatives:** Derive the id from the name or timestamp inside the reducer.
- **Why:** Keeps the reducer pure and lets the first event fully describe the pet.

### D-008 Internal bookkeeping lives in `state.ledger`; UI moments live in `state.reactions`

- **Decision:** Fields the rules need but the spec's public shape does not list (daily counters,
  hunger clock, hibernation flag, wake-up progress, totals) sit in a `ledger` object. Short-lived
  reactions (`yawn`, `victory-dance`, `welcome-back`, `hatched`, …) are cleared by the next non-TICK
  event.
- **Alternatives:** Recompute everything from the event log on each event.
- **Why:** The reducer stays `(state, event) → state` and O(1) per event; the public fields stay as
  specified.

### D-009 Two small rules added to the spec's shape

- **Decision:** (a) Health regenerates +1 per awake hour while satiety ≥ 50. (b) Focus costs
  0.1 energy per minute.
- **Alternatives:** Only "+5 health per session while sick"; energy only moves on overwork/late
  sessions.
- **Why:** Without (a) a single hungry spell would cap health forever; without (b) energy is almost
  always 100 and the "thriving" energy gate is meaningless. Both are constants in `config.ts`.

### D-010 Hunger damage timing

- **Decision:** Once satiety has been below 20 for more than 24 hours, health drops 5 immediately and
  then 5 more at each further 24-hour mark (floor 10). The hunger clock starts at the estimated
  crossing time and resets after hibernation, vacation, or eating above 20.
- **Alternatives:** First penalty only at 48 hours.
- **Why:** Closest reading of "continuously for > 24 hours → −5 per further day".

### D-011 Sessions need an active `SESSION_STARTED`; duplicates are no-ops

- **Decision:** `SESSION_COMPLETED`, `SESSION_ABANDONED` and `DISTRACTION_REPORTED` are ignored when no
  session is active. Minutes are clamped to 0..240. A session left running 120 minutes past its plan
  quietly expires (no reward, no penalty).
- **Alternatives:** Accept standalone completions.
- **Why:** The CLI and VS Code share one log; whichever surface finishes first wins and a second
  completion is harmless. Also blocks accidental 10,000-minute sessions.

### D-012 Natural breaks

- **Decision:** 45 idle minutes between events (no session running) reset `focusMinutesSinceBreak`
  without granting the `balance` trait.
- **Alternatives:** Only explicit `BREAK_TAKEN` resets overwork.
- **Why:** Otherwise a normal day's sessions would trigger the overwork yawn the next morning.

### D-013 Evolution weights

- **Decision:** "Normalized" trait = trait ÷ weight with weights depth 1, sprint 1.5, balance 1.5,
  craft 3, night 1.
- **Alternatives:** Normalize by share of total (does not change the argmax); per-day rates.
- **Why:** Commits and short sessions accrue much faster than deep sessions; the 60-day persona
  simulation confirms each work style lands on its intended species.

### D-014 Out-of-order timestamps

- **Decision:** An event older than the previous one is applied as if it happened at the previous
  event's time. Invalid timestamps likewise.
- **Alternatives:** Reject, or re-sort the log.
- **Why:** Two processes appending concurrently can interleave by a few milliseconds; clamping keeps
  replay deterministic and never runs time backwards.

### D-015 Hibernation and vacation details

- **Decision:** Sessions completed while hibernating still feed the pet; the second within 48 hours
  wakes it. Vacation pauses decay, the hibernation clock and the hunger clock; the day vacation ends
  cannot break the streak.
- **Why:** "No penalties" for coming back, and vacation should feel like a true pause.

### D-016 Personas and species

- **Decision:** The "balanced shipper" persona evolves into a **shipwyrm** (commits + CI + breaks).
  Two extra personas cover **zenpaca** (breaks after every session) and **nocturne** (midnight
  coder).
- **Why:** Testing all five species protects the evolution table during tuning.

### D-017 Time zone math performance

- **Decision:** Cache UTC offsets per 15-minute slice and integrate awake hours a day at a time in
  local wall-clock time (falling back to 15-minute slices across DST changes).
- **Alternatives:** Call `Intl.DateTimeFormat#formatToParts` per slice.
- **Why:** `formatToParts` costs ~80 µs; the change made the 60-day simulation ~10× faster
  (≈ 0.1 ms per event) while staying exact for half-hour zones and DST.

### D-018 Pure helpers shared by every surface live in core

- **Decision:** `buildHistory`, `weekStats`, `buildWeeklyJournal`, `duckQuestion`/`duckSummary` and
  `summarize` are in `packages/core`.
- **Why:** The CLI, VS Code and web app all show the same numbers and words, and core's coverage gate
  protects them.

## M2 — Store + CLI

### D-019 Sprites built early

- **Decision:** Built `packages/sprites` (ASCII, SVG, README card) during M2 rather than M5.
- **Why:** `dmn start`, `dmn status` and `dmn badge` need the art; building it once avoids a
  placeholder pass.

### D-020 Store layout and locking

- **Decision:** `~/.daemonling/events.jsonl` (one JSON event per line, each tagged `"v": 2`),
  `snapshot.json` (cached state + event count), and `events.lock` (exclusive `open(…, 'wx')` lock;
  locks older than 10 s are considered abandoned). Snapshots are written to a temp file and
  renamed. Unreadable lines (e.g. a torn final write) are skipped, not fatal.
- **Alternatives:** SQLite (native dependency, harder to inspect); a single JSON file rewritten on
  every event (lossy on crash).
- **Why:** Human-readable, append-only, trivially backed up, and safe for the CLI and the VS Code
  extension writing at the same time.

### D-021 Example migration

- **Decision:** Record version 1 is a documented pre-release shape (`kind`/`ts`, `SESSION_DONE`,
  `mins`); `migrateRecord` upgrades it to version 2 on read. Records without `v` are treated as v1.
- **Why:** The brief asks for schema versioning with one example migration; this proves the path
  without inventing users who never existed.

### D-022 `dmn start` writes `SESSION_STARTED` immediately

- **Decision:** The start event is persisted before the countdown, so VS Code and `dmn prompt` see
  the running session. Re-running `dmn start` while a session is running re-attaches to it.
  Ctrl+C asks "Were you distracted?"; "y" records `DISTRACTION_REPORTED`, anything else
  `SESSION_ABANDONED`.
- **Why:** One shared truth across surfaces; closing a terminal is recoverable.

### D-023 `dmn break` logs immediately

- **Decision:** `dmn break [minutes]` records the break when typed (no break timer).
- **Alternatives:** A break countdown that only credits the break at the end.
- **Why:** Simpler, and breaks are low-stakes; a timer can come later if beta users ask.

### D-024 `dmn prompt` fast path

- **Decision:** The bundle is split; `dmn prompt` loads only the snapshot reader and a tiny
  formatter, reads the cached snapshot as-is (no decay replay, no time zone math — ICU start-up alone
  costs ~15 ms).
- **Measured:** our code adds ~10 ms on top of bare `node` start-up. In the CI container bare
  `node -e 0` takes ~40 ms, so the prompt is ~50 ms wall there; on a typical laptop it is well under
  50 ms.

### D-025 Extra CLI commands

- **Decision:** Added `dmn settings` (show/change goal, bedtime, wake, grace, time zone, name) and
  `dmn event ci-passed` alongside `dmn event commit`. Running `dmn` with no arguments shows status (or
  help if there is no pet).
- **Why:** Settings must be changeable somewhere in the CLI; CI scripts need a way to celebrate.

## M3 — VS Code extension

### D-026 The extension appends `SESSION_COMPLETED` when the timer runs out

- **Decision:** Every second the extension re-reads the log if it changed on disk (size + mtime),
  and if the active session's planned end has passed it appends `SESSION_COMPLETED`. The CLI does
  the same at the end of its countdown; the reducer ignores the second completion (D-011).
- **Alternatives:** Only the surface that started a session may complete it.
- **Why:** The editor observes focus for the whole session, so its completion is legitimate, and a
  session started in a terminal that was later closed still gets credited while VS Code is open.

### D-027 Focus sensing is a pure state machine with a notification budget

- **Decision:** `apps/vscode/src/focus.ts` turns window focus/blur, session start/stop and ticks
  into effects (`distraction-detected`, `offer-honest-end`). The distraction is reported on return
  (so the exact seconds away are known). Unsolicited notifications are limited to two per local day.
- **Why:** Testable without VS Code, auditable for privacy, and kind by default.

### D-028 VS Code settings feed the shared pet

- **Decision:** Changing `daemonling.dailyGoalMinutes` or `daemonling.graceSeconds` appends a
  `SETTINGS_CHANGED` event, so the CLI sees the same goal and grace period.
- **Why:** One pet, one set of rules, whichever surface you use.

### D-029 Activation is tested against an in-memory `vscode` stub

- **Decision:** Vitest aliases `vscode` to `apps/vscode/test/vscode-stub.ts` and drives
  `activate()` end to end (hatch → start → blur/focus → distraction → den → menu → settings).
- **Alternatives:** `@vscode/test-electron` (downloads VS Code; needs a display and network in CI).
- **Why:** Fast and offline; the remaining risk (real VS Code API behaviour) is small and covered by
  manual testing of the `.vsix`.

## M4 — Web home

### D-030 Hand-written service worker instead of `vite-plugin-pwa`

- **Decision:** `apps/web/public/sw.js` (~40 lines): precache the shell, cache-first for same-origin
  GETs, fall back to `index.html` offline. Registered only in production builds.
- **Alternatives:** `vite-plugin-pwa` (Workbox).
- **Why:** Fewer dependencies, easy to audit for the "no network calls" promise, and enough for a
  single-page app with hashed assets.

### D-031 The web app keeps its own pet (IndexedDB); export/import bridges devices

- **Decision:** Browsers cannot read `~/.daemonling`, so the web home stores its own event log in
  IndexedDB. `dmn export` → web "Import JSON" (and the reverse with `dmn import`) moves a pet between
  them. Tabs stay in sync through a `BroadcastChannel`.
- **Alternatives:** A local HTTP bridge from the CLI (a network listener on the user's machine —
  more attack surface); cloud sync (out of scope for a local-first MVP; see ARCHITECTURE.md).
- **Why:** Honest local-first behaviour with zero servers.

### D-032 Display-time ticking

- **Decision:** The app re-renders every second and applies a `TICK` in memory to show decay and
  hibernation, without persisting an event each second.
- **Why:** Live UI without bloating the log.

### D-033 No router, no chart library

- **Decision:** Five tabs with ARIA `tablist`/`tab`/`tabpanel` semantics and arrow-key navigation;
  the week chart is plain SVG.
- **Why:** 87 KB gzipped total, offline-friendly, and accessible by construction. An axe-core audit of
  every screen in both themes reports zero violations.

### D-034 Relative base path

- **Decision:** `vite.config.ts` uses `base: './'`.
- **Why:** The same build works at `https://<user>.github.io/daemonling/`, at a custom domain root,
  or opened from any sub-path, with no per-environment configuration.

## M5 — Developer-native extras

### D-035 `dmn badge --from <export.json>` for CI

- **Decision:** The card can be rendered from an export file, as of the export's last event.
- **Alternatives:** A hosted badge service (requires uploading data — breaks the privacy promise).
- **Why:** Lets users keep a profile card fresh in their own GitHub Actions while choosing exactly
  what they publish.

### D-036 Expressions that never suggest death

- **Decision:** The "sick" pet has droopy, dizzy eyes rather than X-eyes; "sad" uses raised inner
  brows (not angry ones).
- **Why:** The pet never dies; the art must not imply it.

### D-037 Rubber duck is always available

- **Decision:** `dmn duck` works from day one; learning the `rubber-duck` trick (7-day streak) is a
  celebration, not a gate. BYO-LLM duck mode stays on the roadmap only.
- **Why:** Never withhold a genuinely useful debugging aid as a reward.
